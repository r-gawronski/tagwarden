# Threat Model (draft)

Status: living document. Update it whenever a change touches a trust boundary: network paths, credentials or signatures.

Method: STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege).

## System summary

Tagwarden mirrors selected container images and Helm charts from upstream registries into a target OCI registry inside an air-gapped network.

- `ClusterMirrorTarget` (cluster-scoped, owned by the platform team) defines the target registry, credentials Secret, CA bundle, proxy settings, allowed sources, the projects tenants may push to with the namespaces allowed to use each one, and default policy.
- `ArtifactMirror` (namespaced, owned by tenants) defines a source, artifact type, tag filters, schedule, verification and prune settings.
- The controller renders each `ArtifactMirror` into a CronJob in the operator namespace (`tagwarden-system`). Sync Jobs never run in tenant namespaces. The link is cross-namespace, so cleanup uses a finalizer on the `ArtifactMirror` and labels on the CronJob, not ownerReferences.
- The Job runs the same binary in `sync` mode. It lists upstream tags through the proxy, selects tags, verifies signatures, copies by digest (index and referrers) and reports the result in its termination message.
- Sync Jobs never call the Kubernetes API. They run under a dedicated ServiceAccount with `automountServiceAccountToken: false`.
- `VulnerabilityException` (cluster-scoped, owned by the security team) allows a known vulnerability through the scan gate until it expires.
- Phase 1 has no admission webhook. Validation is CEL in the CRD schema plus the same checks in the controller at reconcile time.

## Roadmap phases

Each mitigation names the phase that delivers it.

| Phase | Scope |
|-------|-------|
| 1 | MVP images: CRDs with CEL validation, tag selection, proxy and CA transport, sync engine by digest, CronJob controller, Helm chart for the operator, signed operator images |
| 2 | Helm chart sources: OCI and classic repositories with `.prov` |
| 3 | Supply chain: cosign verification with offline trusted root, referrers copy, re-signing with a KMS key, SBOM, Trivy gate, `VulnerabilityException` |
| 4 | Lifecycle: prune of operator-created tags, tag mutation policy, registry tag immutability |
| 5 | Hardening and operations: metrics, OTel, audit log, NetworkPolicy per Job, FIPS build, concurrency limits |
| 6 | Release and open source: goreleaser, SLSA L3, Scorecard publishing, public repository |

## Assets

| Asset | Why it matters |
|-------|----------------|
| Target registry content | Everything in the air-gapped network pulls from it. Poisoned content runs in production. |
| Target push credentials | Push access to the target registry. Stored in a Secret in the operator namespace, referenced by `ClusterMirrorTarget`. |
| Upstream pull and proxy credentials | Access to private upstream sources and to the egress proxy. |
| Source pull credentials | Accounts at private upstreams, from `ClusterMirrorTarget.sourceCredentials`. Whoever holds them can pull what the account can see. |
| Cloud workload identity | The Microsoft Entra identity in `ClusterMirrorTarget.workloadIdentity`, and the tokens derived from it at run time: the projected ServiceAccount token, the Entra access token and the registry refresh token. Whoever holds them can push or pull what the identity's role assignments allow. |
| Source CA trust | Extra roots from `sourceCABundles`. Whoever holds such a CA key can impersonate its source registry. |
| Proxy CA trust | The CA bundle used to trust a TLS-inspecting proxy. Whoever holds that CA key can impersonate any upstream. |
| Verification config | Cosign trusted root and signer identities. Whoever changes them decides what counts as signed. |
| Signing keys (phase 3) | KMS or HSM keys used to re-sign mirrored artifacts. They vouch for content inside the network. |
| Operator image | Runs with controller RBAC and runs every sync Job. A compromised image compromises every mirror. |

## Trust boundaries

1. **Upstream registries over the internet.** Untrusted. Reached only through the HTTPS proxy.
2. **Proxy with TLS inspection.** Fully trusted for content until phase 3 signature verification. It can read and modify traffic if Tagwarden trusts its CA.
3. **Operator namespace.** The controller, CronJobs, sync Jobs, target credentials, source credentials and source CAs live here. Tenants have no access.
4. **Tenant namespaces.** Tenants create `ArtifactMirror` objects and nothing else that Tagwarden acts on.
5. **Target registry.** Trusted store. Tagwarden writes to it with push credentials or a cloud workload identity.
6. **Platform team and security team.** Only the platform team creates `ClusterMirrorTarget` objects. Only the security team creates `VulnerabilityException` objects.
7. **Cloud identity provider.** Microsoft Entra ID or AWS STS, reached through the proxy, issues registry tokens for the workload identity of a target (with ACR or ECR).

| T1 | Compromised upstream image (malicious content published under a valid tag) | T | Allow only sources listed in `ClusterMirrorTarget.allowedSources`. | T2 | Upstream tag mutation (existing tag re-pointed to new content) | T, R | Resolve each tag to a digest once and copy by digest. Record the mirrored digest. Detect when an upstream tag now points to a different digest, refuse to overwrite the target tag and report it. Use registry tag immutability where the target supports it. | 1: digest-first copy. 4: mutation policy, immutability |
| T3 | Proxy MITM or abuse of the TLS-inspection CA | S, T | Trust the proxy CA only in the sync Job, from an explicit CA reference, never system-wide. Never skip TLS verification. Digest checks do not help here: the proxy also serves the tag-to-digest resolution, so it can return a forged manifest with matching blobs. Until phase 3 the proxy CA is fully trusted. Whoever holds its key can replace any mirrored artifact. Signature verification against pinned identities and an offline trusted root (T19) closes this. | 1: CA scoping, no skip-verify. 3: cosign |
| T4 | Stolen target push credentials | S, E | Credentials live only in a Secret in the operator namespace (T14). Use a robot account scoped to the mirror projects with push and pull only. Document rotation. Re-signing with a KMS or HSM key lets consumers reject artifacts pushed with a stolen token but not signed. | 1: scoping, docs. 3: re-sign |
| T5 | Tenant mirrors into another tenant's project | E | `ClusterMirrorTarget.projects` lists every project a mirror may push to, each with a required `namespaceSelector`. A mirror may push only to a listed project whose selector matches its namespace. A shared project such as `mirror` with an empty selector (`{}`) lets all teams share mirrored sources. Team projects use label selectors. The target path derives from the target config and the source (T17), not from free user input; an override needs a project that allows it (T23). CEL in the CRD schema rejects malformed paths. The controller checks at reconcile that the project is listed and its selector matches the labels of the mirror's namespace. On failure it sets Ready=False with reason `ProjectNotAllowed`, records an Event and removes the CronJob and spec ConfigMap. Namespace label changes trigger a re-check. | 1: controller enforcement in place |
| T6 | Tenant mirrors from a disallowed source | E, T | CEL rejects malformed source references. `allowedSources` applies to every project of a target, so a team that needs a source other teams must not use gets its own target. CEL cannot read `ClusterMirrorTarget`, so the controller checks the source against `allowedSources` at reconcile. The controller passes `allowedSources` in the Job spec, and the sync Job re-checks the source registry before any network call: exact `host[:port]` match, case-insensitive, with `docker.io`, `index.docker.io` and `registry-1.docker.io` treated as one registry. A mismatch fails the Job with a config error. The controller uses the same check and sets Ready=False with reason `SourceNotAllowed`, also for a source that is a literal internal address (T16), and renders no CronJob. | 1: controller and Job enforcement in place |
| T7 | ReDoS or resource exhaustion through tag filters | D | Go `regexp` uses RE2, which runs in linear time. Cap the number of patterns and their length in CEL. Reject a pattern whose compiled program exceeds 2000 instructions. Cap the semver constraint length. Reject invalid patterns and constraints at reconcile. | 1 |
| T8 | Credential leakage through status, logs, Events or errors | I | Credentials come only from Secret references. This covers target push, upstream pull and proxy credentials. Never write them to status, Events, logs, errors or the termination message. Redact userinfo in every URL before it reaches an error or log, including proxy URLs of the form `user:pass@host`. Redact auth headers in transport debug logs. Tests assert that secret values do not appear in any of these outputs. | 1 |
| T9 | Operator image compromise (project supply chain) | T, E | Pin GitHub Actions by commit SHA. Least-privilege workflow permissions. `govulncheck` and CodeQL in CI. Distroless nonroot base. Signed operator images. SLSA L3 provenance and published Scorecard results. | 1: CI hardening, signed images. 6: SLSA L3, Scorecard |
| T10 | Resource exhaustion by one tenant: frequent schedules, many mirrors, many tags or huge images fill the operator namespace, the proxy, upstream quotas or the shared registry disk | D | `keepLatest` capped at 100 in CEL. CronJob `concurrencyPolicy: Forbid`, `activeDeadlineSeconds` and resource limits on sync Jobs. `ClusterMirrorTarget.spec.limits`, checked by the controller at reconcile, with defaults when absent: `minSyncInterval` (default 1h, at least 5m) is compared with the gaps between the runs of the schedule over the next five years, parsed as the CronJob controller parses it, and a more frequent schedule gets Ready=False with reason `ScheduleTooFrequent`. `maxKeepLatest` (default 20) and `maxExplicitTags` (default 50) refuse larger tag selections, and `maxMirrorsPerNamespace` (default 50) allows only the oldest mirrors of a namespace that use the target, by creation time and then name, counting every mirror not being deleted; the rest get `LimitExceeded`. A refused mirror loses its CronJob, gets an Event and owns no path (T17). Deleting a mirror re-checks the others of its namespace and target. `maxArtifactSize` (no default) goes to the Job in the spec: before copying a digest, the Job sums the config and layer sizes that the manifest declares, over every manifest of an index, and refuses a larger artifact as a failed tag with nothing copied. A layer shared by several platforms counts once per platform, so the sum can only overstate the size. ggcr checks each image blob against its declared size during the copy. The referrers and cosign tag-scheme artifacts the Job copies for one artifact in a run share a separate budget of the same size; over it, the tag fails and does not move, though the image may already be on the target, as with other referrer failures. Referrers already on the target do not count, so a source can add up to the limit in referrers per run. A `tagwarden.dev/sync-now` request needs only `patch` on the tenant's own `ArtifactMirror` and is rate limited the same way: the controller starts its Job only when no Job of the mirror runs at the time the request is handled and `minSyncInterval` has passed since the last Job started, scheduled or requested; otherwise the request waits (`Deferred`). A scheduled run may still overlap a requested Job, because the CronJob's `Forbid` policy does not count Jobs it did not create; the sync is idempotent by digest, so the overlap costs duplicate pulls only. A suspended or refused mirror refuses requests. The Job comes from the CronJob template; the annotation value only names the Job, by hash, so one request starts at most one Job. Kubernetes ResourceQuota on `count/artifactmirrors.mirror.tagwarden.dev` and registry project quotas complement these limits (docs/install.md). | 1: caps, limits. 5: global and per-Job concurrency limits |
| T11 | Privilege escalation from the sync Job pod | E | Dedicated ServiceAccount with `automountServiceAccountToken: false`. Distroless nonroot, read-only root filesystem, all capabilities dropped, seccomp `RuntimeDefault`, no privilege escalation. Only the target credentials, the target and proxy CAs, the target client certificate, the source credentials and CA of the pod's own source (T24, T25) and, for Azure or AWS auth, a projected token for the Entra or STS audience (T26, T28) are mounted, at fixed paths. Proxy credentials come in as env from a Secret reference. Tenant fields reach the Job only through the spec file in a ConfigMap, never as image, command, env or volumes. The controller renders the pod with the `tagwarden-sync` ServiceAccount, or `workloadIdentity.serviceAccountName` for Azure auth (no RBAC bindings in either case), `enableServiceLinks: false`, resource limits, and Secrets only as volume or `secretKeyRef` references, never as values. Exit code 3 (config error) fails the Job without retries. A hand edit of the `tagwarden.dev/` pod labels, image, args, ServiceAccount, token mount, security contexts, host namespaces and aliases, DNS config, node, runtime class, pull secrets, volumes, mounts or env of a sync CronJob is reverted on the next reconcile. | 1: controller rendering in place |
| T12 | Tampered or forged sync result | R, T | The controller treats the termination message as untrusted input. It reads it only from a pod controlled by the mirror's Job, refuses a message over 4096 bytes, of another version, with negative counts or with an invalid tag or digest, and then reports `Crashed` instead. Unknown fields are ignored. Quoted errors are cut to 256 bytes. The report only fills in status and Events; it never decides what a mirror may do. Mirrored digests can be checked against the target registry. | 1: controller enforcement in place |
| T13 | Prune deletes content the operator did not create, or still in use | T, D | Prune only tags recorded as created by Tagwarden. Prune is opt-in per `ArtifactMirror`. A tag shared by several mirrors is deleted only when no mirror selects it any more (T17). | 4 |
| T14 | Target credentials exposed to tenants | I, E | Sync Jobs and CronJobs run only in the operator namespace. Target push credentials never leave it. No tenant pod mounts them. The controller reads Secrets only in its own namespace. | 1 |
| T15 | Controller privilege escalation | E | The controller creates Jobs, CronJobs and ConfigMaps only in its own namespace, through a Role, not a ClusterRole. It reads Secrets only in its own namespace. Cluster-wide access is limited to Tagwarden CRDs. RBAC markers are the source of truth and are reviewed on every change. | 1 |
| T16 | SSRF or lateral movement from a sync Job through crafted sources or redirects | S, E, I | The sync Job reaches the network only through the proxy. Refuse link-local, cloud metadata, loopback and cluster pod and service CIDRs as source hosts, at reconcile and in the Job. The Job resolves the source host itself before any network call and refuses it if any address is loopback, link-local, unspecified, in `0.0.0.0/8`, a metadata address (`169.254.169.254`, `fd00:ec2::254`, `100.100.100.200`), a NAT64 address (`64:ff9b::/96`) that embeds one of these, or inside `deniedCIDRs` (the controller fills in the pod and service CIDRs). The source transport repeats this check on the host of every request, including each redirect hop, and on the resolved address of every direct connection, so a name cannot be rebound between check and connect. Connections to the proxy itself are not checked. `allowedSources` applies to the first source host only, not to redirect hosts, because registries redirect blob downloads to storage hosts. Limitation: with a proxy, the proxy resolves names, not the Job. The Job check catches literal internal addresses and names that the cluster DNS maps to internal addresses, but not a name that only the proxy resolves to an internal address. When a request goes through the proxy, any lookup error passes, because the proxy resolves the name and its ACL is the control; this covers NXDOMAIN, common in air-gapped clusters. Each host is resolved once per run. During the startup window (below) a temporary lookup error (timeout, server failure, refused query) is retried and not cached, so a race at pod start neither fails the run nor lets a proxied host skip the check. NXDOMAIN is not retried. Without a proxy a lookup error fails the run as transient (exit 1), and every direct connection is still checked on its resolved address at dial time. Refusals are config errors (exit 3). The Job ignores proxy variables other than the `HTTPS_PROXY` and `NO_PROXY` the controller sets. The proxy's own ACL must also deny internal ranges, because the proxy resolves names. Sync pods carry `tagwarden.dev/target` (the target name, or `h-` and a sha256 prefix when the name is not a valid label value) and `tagwarden.dev/egress` (`proxy` or `direct`), so cluster admins can enforce the egress path per target with NetworkPolicies: `proxy` pods reach only the proxy, the target and DNS. The controller reverts hand edits of these labels. NetworkPolicy enforcement at pod start is CNI-dependent (kindnet, for example, can pass the first packets of a new pod), so the in-Job checks are the primary control. Other CNIs (the k3s embedded NetworkPolicy controller, for example) reject a new pod's packets until its allow rules are programmed, about a second after start. Only during the first ~35 s of a run, which ends early at the first successful request, both transports retry a request whose connection to the registry or the proxy failed at dial time (refused, unreachable, timeout, temporary DNS failure), with exponential backoff up to about 30 s per request. Nothing was sent on such a connection. Refusals by the host and connect checks are never retried, nor are TLS errors, proxy authentication failures or errors after a connection was set up. | 1: host, redirect and connect checks, egress labels. 5: NetworkPolicy |
| T17 | Target path collision (two sources write the same target repository) | T | The default target path is `<project>/<source-registry>/<source-repo>`, for example `mirror/docker.io/library/nginx`. Different sources never collide by default. Several mirrors may share a target repository when they have the same source: their tag sets are unioned and each tag records which mirrors selected it. If a different source maps to an already-claimed path, which is only possible through an explicit target override in a project that allows it (T23), the controller sets Ready=False with reason `TargetConflict` and does not sync. The oldest mirror (by creation time, then namespace and name) that is allowed to use the project and within the target's limits (T10) owns the path, so a refused mirror cannot block it. Sources compare after folding the Docker Hub names and adding the implicit `library/` prefix. The default path turns `host:port` into `host-port`, which can collide with a registry whose host name is literally `host-port`; the sources differ, so the conflict check catches it. The controller never updates or deletes a CronJob or ConfigMap whose annotations name another mirror (`OwnershipConflict`). The check covers mirrors of the same `ClusterMirrorTarget`. Phase 2: include artifact type in canonical source comparison. | 1: controller enforcement in place. 2: artifact type in source comparison |
| T18 | `VulnerabilityException` abuse (tenant approves its own exception) | E, R | `VulnerabilityException` is cluster-scoped. A separate ClusterRole held by the security team grants write access. Tenants have none. Every exception has an expiry and an approver. The controller ignores expired exceptions. | 3 |
| T19 | Forged or stale cosign trust root, or changed signer identities | S, T | Verification runs offline against a trusted root delivered with the operator or from a Secret in the operator namespace, never fetched through the proxy at verify time. Reject a trusted root past its validity and document how to refresh it. Signer identities are set per allowed source in `ClusterMirrorTarget`, so only the platform team can change them. Tenants cannot disable verification that the target requires. | 3 |
| T20 | Repudiation: no record of who mirrored what | R | Status and Events record the mirrored digests per tag. An audit log records each sync: the requesting `ArtifactMirror`, source reference, digest, target reference, verification result and time. The Kubernetes audit log records who created or changed the `ArtifactMirror`. | 1: status, Events, one JSON line per artifact on the Job stdout. 5: audit log |
| T21 | Tampered classic Helm repository | T, D | Require HTTPS for repository and chart URLs. Verify `.prov` against a per-source keyring when configured. Cap the `index.yaml` size. Resolve relative chart URLs against the index URL and apply the source host checks (T16) to absolute ones. | 2 |
| T23 | Path squatting in a shared project: a tenant sets `target.repository` to the default path of another source, for example source `ghcr.io/someone/nginx` with `target.repository: docker.io/library/nginx`. As the older mirror it owns the path (T17), the real mirror gets `TargetConflict`, and workloads pulling `<project>/docker.io/library/nginx` get the tenant's image. `allowedSources` does not help when a registry hosts many publishers. | S, T | The target path always derives from the source (`<source-registry>/<source-repository>`). An explicit `target.repository` that differs from it is allowed only in projects with `allowRepositoryOverride: true` (default false), meant for projects owned by a single team. Otherwise the controller sets Ready=False with reason `RepositoryOverrideNotAllowed`, records an Event, removes the CronJob and spec ConfigMap and does not count the mirror as an owner of the path. Changing the flag on the target re-checks its mirrors. Default paths are unique per source only if no two `allowedSources` of different registries map to the same path segment (for example `reg:5000` and `reg-5000`, or `[2001:db8::1]:5000` and `2001-db8--1-5000`); the controller enforces this and sets the target Ready=False with reason `AmbiguousAllowedSources` and an Event. | 1: controller enforcement in place |
| T24 | Source credentials exposed to tenants or to other sources | I, E | `sourceCredentials` is set only on `ClusterMirrorTarget`, so only the platform team decides which sources have accounts. The Secrets stay in the operator namespace (T14). A sync pod mounts only the Secret of its own source registry, read-only, at a fixed path. A mirror of another source never gets it. Sync Jobs read only static `auths` entries: credential helpers are refused. Values never reach status, Events, logs, errors, the spec ConfigMap, env or the termination message (T8); tests assert it. A tenant cannot point the credentials at another host: sources are limited to `allowedSources` (T6). The registry library sends the Authorization header only to the source registry and to the token realm it names, never to redirect hosts such as blob CDNs, for which it fetches tokens anonymously. The realm host is chosen by the source registry and is not restricted beyond the internal-address checks (T16). Accepted: a source registry can already obtain its own account's credentials. | 1 |
| T25 | A private CA widens trust for every upstream | S, T | `sourceCABundles` is set by the platform team. The CA is mounted only in sync pods of that source, and trusted there for every host the source transport reaches (the registry, its redirect and token hosts), never for the target. The sync Job adds it to the source transport pool next to the system roots and the proxy CA. The CA Secret must hold PEM certificates, or the target is not Ready. TLS verification is never skipped. This replaces the earlier workaround of putting a source CA into `proxy.caBundleSecretRef`, which trusted it for the proxy and every source. | 1 |
| T26 | Stolen or misused workload identity tokens | S, I, E | Pods that use Azure auth mount only a projected ServiceAccount token with audience `api://AzureADTokenExchange` and a one-hour lifetime. The Kubernetes API rejects that audience, so the token grants nothing in the cluster; `automountServiceAccountToken` stays false. The ServiceAccount is created by the platform team in the operator namespace with no RBAC bindings; the controller only references it and needs no RBAC for ServiceAccounts. Other pods keep `tagwarden-sync` and get no token at all. The Job re-reads the token file at the start of each run, then holds the Entra access token and the registry refresh token in memory only. None of them reach status, Events, logs, errors, the spec ConfigMap or the termination message; errors carry the HTTP status and OAuth and Entra error codes only, never response bodies or `error_description`. Tests assert it. Token requests do not follow redirects, so the assertion never goes to another host. The client ID, tenant ID and authority host are identifiers, not secrets, and travel in the spec ConfigMap. Federated credentials match the ServiceAccount, so targets with different identities need their own ServiceAccounts: with a shared one, a pod of one target holds a token that the other identity accepts (docs/install.md). Accepted: every mirror of a target shares its identity and the federated credential subject, so a mirror can use the identity's rights on any registry that the target lists for it; scope the identity with role assignments and use separate targets for different rights. A tenant cannot name another registry: the push goes to `spec.registry` and pulls are limited to `allowedSources` (T6). | 1 |
| T27 | Forged token endpoint, wrong token audience or wrong token recipient | S, T, I | `authorityHost` is set only by the platform team on `ClusterMirrorTarget` and must be one of the known Microsoft Entra hosts (`login.microsoftonline.com`, `login.microsoftonline.us`, `login.partner.microsoftonline.cn`, `login.chinacloudapi.cn`), in CEL and again in the Job. The Entra scope is fixed to `https://containerregistry.azure.net/.default`, so the Job never mints a Resource Manager token and never sends one to a registry. Azure auth is allowed only for Azure Container Registry login servers (`*.azurecr.io`, `*.azurecr.us`, `*.azurecr.cn`, port 443 at most), in CEL for the target and each source entry, and again in the Job before the exchange; any other host is a config error before a token request. Token calls use the source or target transport, so TLS verification, the proxy, the proxy CA, the source CA for source pulls, the internal-address checks for the source path (T16) and the startup retry window apply to them. The registry token exchange always uses HTTPS to the registry host itself. The registry library then sends the ACR refresh token to the token realm the registry names, the same trust as dockerconfigjson credentials (T24); the refresh token is valid only for that registry. Whoever controls an allowed authority host, or a CA trusted for it, receives the projected token, which only Entra accepts and only for this identity's federated credential. | 1 |
| T28 | Stolen or misused AWS web identity tokens and credentials | S, I, E | Pods that use AWS auth mount only a projected ServiceAccount token with audience `sts.amazonaws.com` and a one-hour lifetime, at their own path next to any Azure token. The Kubernetes API rejects that audience; `automountServiceAccountToken` stays false. The ServiceAccount is created by the platform team with no RBAC bindings, as in T26. The Job asks STS for a 15-minute session with a fixed session name derived from the mirror, uses it to sign one ECR call and holds the token, the access key, secret key, session token and ECR password in memory only. None of them reach status, Events, logs, errors, the spec ConfigMap or the termination message; errors carry the HTTP status and the AWS error code only, never response bodies or messages. Tests assert it. STS and ECR calls do not follow redirects. The role ARN and region are identifiers and travel in the spec ConfigMap. The role trusts the ServiceAccount, so targets with different roles need their own ServiceAccounts (docs/install.md). EKS Pod Identity is not supported because its agent is on a link-local address (T16). Accepted: every mirror of a target shares its role and can use its rights on any registry the target lists for it; scope the role per target. | 1 |
| T29 | Wrong STS or ECR endpoint, or a registry token for the wrong recipient | S, T, I | There is no endpoint field: the STS (`https://sts.<region>.amazonaws.com`) and ECR API (`https://api.ecr.<region>.amazonaws.com`, `ecr-fips` for FIPS registries, `amazonaws.com.cn` in China) URLs are derived from `region`, which CEL and the Job restrict to the commercial, China and GovCloud partitions and to the partition of `roleARN`. AWS auth is allowed only for ECR private registry hosts (`<account>.dkr.ecr[-fips].<region>.amazonaws.com[.cn]`, port 443 at most), in CEL for the target and each source entry, and again in the Job, which also refuses a registry in another region than `workloadIdentity.aws.region` before any token call. Token calls use the source or target transport, so TLS verification, the proxy and its CA, the source CA for source pulls, the internal-address checks for the source path (T16) and the startup window apply. The ECR password is valid for every registry the role may access in that region, and goes only to the checked registry host, the same trust as dockerconfigjson credentials (T24). Whoever controls a CA trusted for the AWS hosts receives the projected token, which only STS accepts and only for roles that trust this ServiceAccount. | 1 |
| T22 | Unbounded upstream tag lists | D | Cap the number of pagination pages per source. A listing of more than 10000 tags stops with an error instead of a truncated list, so the selection never runs on partial input. The error is reported in status. | 1 |

## Compliance items

These are requirements of regulated environments, not threat mitigations.

- FIPS 140 build variant of the operator image. Phase 5.

## Resolved questions

- Signer identities for cosign verification are configured per allowed source in `ClusterMirrorTarget` and changed only by the platform team (T19).
- The target path is derived from the source by default. An explicit override needs `allowRepositoryOverride` on the project (T23) and cannot claim a path owned by another source (T17).
- Audit trail: status and Events in phase 1, a dedicated audit log in phase 5 (T20).

## Open questions

- Distribution format of the offline trusted root: bundled in the image, a Secret, or both.
- Whether tenants may add stricter signer identities on top of those in `ClusterMirrorTarget`.
